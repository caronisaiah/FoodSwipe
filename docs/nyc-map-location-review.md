# NYC location approval review

Eight Overture points are ready for explicit staging approval. Au Cheval and Smacking Burger stay pending. IDs below are the existing public FoodSwipe IDs (profile slugs). The [staging approval SQL](../scripts/stage-nyc-map-approvals.sql) resolves each slug to its existing database ID and checks the exact feature, release, point, and source before approving it.

The check compares operator-published addresses with [NYC Planning GeoSearch](https://geosearch.planninglabs.nyc/docs/) Property Address Directory (PAD) points and [NYC Building Footprints](https://data.cityofnewyork.us/City-Government/BUILDING/5zhs-2jue/about_data) polygons joined by building identification number (BIN). [NYC restaurant inspections](https://data.cityofnewyork.us/resource/43nn-pn8j.json) corroborate several business-to-building matches. Distances are approximate horizontal offsets, not surveyed door locations. Overture confidence is the provider’s estimate of whether the place exists, distinct from the position review. The [original extraction](overture-nyc-matches.json) retains source-level notices and unrounded coordinates for release `2026-10-21.0`. All nine IDs were confirmed in the [Overture GERS registry](https://docs.overturemaps.org/gers/registry/).

## Smacking Burger

The [restaurant website](https://smackingburger.com/) lists 51–63 8th Ave, New York, NY 10014, USA. City inspection CAMIS 50153998 records the business at number 63 on BBL 1006160046 / BIN 1011074. GeoSearch returns separately mapped addresses for 51 and 63 on different parcels, about 63 m apart. [Eater’s venue listing](https://ny.eater.com/venue/106577/smacking-burger) independently identifies the restaurant inside the gas station at number 63. This narrows the target property, but the Overture gas-station listing does not identify a restaurant pin.

Mapbox Geocoding v6 can return address and optional entrance features with `permanent=true`. Indefinite storage is available for properly authorized permanent results and requires a valid card or enterprise contract. Mapbox limits these results to the account holder’s use and restricts distribution or sublicensing. FoodSwipe sends numeric coordinates to a public browser, so confirm specifically that the account terms cover this display before storing a result for this feature. The browser QA token is authorized for tile testing. A separate permanent-geocoding request and coverage of public coordinate delivery were unavailable. No result has been obtained or stored. [Geocoding v6](https://docs.mapbox.com/api/search/geocoding/#storing-geocoding-results) · [Mapbox pricing and use terms](https://www.mapbox.com/pricing)

With that authorization in place, submit the publisher address and check the returned address feature, address/ZIP match, reported accuracy, and any entrance against the City’s number-63 property and the business entrance. Reject an interpolated street result or a pin on number 51. If verified, retain the response ID, request mode, source date, verified coordinates and account terms under `mapbox_permanent` in a provider-aware record. The current location table is Overture-specific, so adding that provider would require a separate schema change. It should never be inserted under an Overture ID.

## Staging and live QA

Follow the [local migration and pending import instructions](overture-mapbox.md#prepare-local-staging). After reviewing the table above, apply the batch explicitly from the repository root:

```sh
psql -X -h localhost -d foodswipe_map_staging \
  -v reviewer='Your name' -f scripts/stage-nyc-map-approvals.sql
```

The approval is transactional and scoped to the eight verified rows. A missing, hidden, rejected, or changed record aborts the batch. A rerun preserves the metadata of already-approved rows. It writes only `restaurant_locations`. Production must keep `FOODSWIPE_MAP_ENABLED` unset or false. Browser testing uses `MAPBOX_PUBLIC_TOKEN` from the ignored local environment file and a local staging database.

QA ran against disposable PostgreSQL with the eight reviewed points, fixture profiles and videos, one pending location, and one synthetic approved location whose restaurant was hidden. The approval rolled back on a changed coordinate and left the profile, video, and hero-selection tables untouched. The public API still returned the same ten profiles and twenty real-source videos before and after the test.

Live Mapbox Standard styles and tiles loaded on localhost in desktop Chrome and a touch viewport. Both runs exposed eight pins, hid pending and hidden restaurants, and exercised the Emily preview, profile navigation, Back, pan, and zoom. Mapbox, OpenStreetMap, and Overture source attribution were present. The swipe feed made no Mapbox requests, and the map made no Google Places, Overture, or geocoding requests. Physical-device QA and applying the batch to a persistent staging database remain outstanding.

Separately, the existing Google importer stores business names, addresses, and coordinates on candidates. Promotion copies them to the public catalog without inheriting expiry, and source records retain duplicate names and addresses. See the [Google retention plan](map-discovery.md#existing-retention-and-migration) for the outstanding inventory, replacement, and deletion work.
