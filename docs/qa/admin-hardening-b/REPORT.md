## 3. Audit schema and taxonomy
`admin_events`: `seq` (identity, ordering/cursor), `id`, `occurred_at` (DB time), `action`, `resource_type`, `resource_id` (stable id), `related_resource_type/id`, `actor_identity`, `auth_scope`, `actor_assurance`, `request_id`, `changes` (`{field:{from,to}}`, allow-listed fields only, values > 1000 chars clipped), `details` (small, non-secret), `reason`. CHECKs: scope, non-blank actor/request/resource, payload size bound. Indexes on resource, related, request, time. Triggers reject UPDATE / DELETE / TRUNCATE.
Taxonomy (23 actions, 6 categories: draft modification, approval, publication, edit, removal, recovery) is in `docs/admin-audit-log.md`. Covered: candidate create/edit/market change/approve/reject/status, hero select/clear/inherit, promotion, published restaurant edit/hide/restore, video candidate create/edit/approve/reject, attach, direct add, published video correct/hide/restore.

## 4. Credential attribution model and its limits
Actor = non-secret label of the credential that authenticated: `publish-credential` / `draft-credential`, or operator labels from optional `FOODSWIPE_ADMIN_PUBLISH_LABEL` / `FOODSWIPE_ADMIN_DRAFT_LABEL` (validated; invalid values ignored). Plus `auth_scope` and `actor_assurance = "shared-credential"` on every event, and on the audit screen.
Limits: two shared secrets, so at most two actors are distinguishable; several agents sharing the draft secret look identical; an `approved` event means "the publication credential approved", **not** that a named human reviewed the content. Real per-person/per-agent proof needs per-user authentication (future work). Hardening A's permission boundaries are unchanged (the authorization matrix passes: 835 assertions over 27 routes, with the new routes declared). A reason that contains a configured secret is refused.

## 5. Transactional guarantees
Each mutation is **one SQL statement** (data-modifying CTE): `prev` (locked before image) → change → `admin_events` insert. Statement atomicity means the change and its event commit together or not at all; audit failure aborts the mutation (HTTP 500), nothing is swallowed. Event is written only if an allow-listed field really changed, computed in-statement (so exact "from" values, no events for no-ops, repeats, misses or refusals). Verified on real PostgreSQL by forcing the audit insert to fail (trigger that raises) for 11 mutation types including promotion (multi-table), attach (live video + candidate status + event) and route level: every table was byte-identical afterwards. A static test fails if any app code writes an audited table outside the audited helpers (proven to catch a violation).
Not a guarantee: direct-add is **not atomic as a whole**; it is three separately atomic audited steps under one request id. Failure of each step was tested on PostgreSQL (see the pre-commit section): earlier steps stay committed and the log says exactly what happened.

## 11. Migration and rollback
Migration safety proven on PGlite: applying 0013 on a database as production is today (rows incl. three `needs_review` restaurant drafts and an unattached video candidate) leaves every row byte-identical; no events backfilled (history starts empty, nothing implies historical actors); a migration that fails part-way leaves no table, no triggers and no migration record. Apply the whole file in one transaction (`psql -1 -f` or the Neon SQL editor as one script), *not* `db:push` (it would skip the triggers), **before** deploying the code (until then audited mutations fail closed, tested). **Recoveries** (full text in `docs/admin-audit-log.md`): rolling back the *code* keeps `admin_events`, its events and triggers (the normal production rollback; never `DROP` or rename the table); a failed migration leaves nothing behind and is re-run, with an owner-run cleanup that refuses once events exist; a deployed defect is corrected with new audited changes, never by editing events.
